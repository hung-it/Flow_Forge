# Vận hành local và CI

## GitHub → GitLab
Trạng thái 2026-11-15: người dùng xác nhận chưa có GitLab project/runner; GitHub repo chưa có
variables/secrets đồng bộ (đã kiểm tra metadata, không đọc/in log credential).
Đây là bước thiết lập còn chờ; nghiệm thu local không chứng minh remote CI.

Khi bắt đầu remote CI:
1. Tạo GitLab project trống và chọn hosted runner phù hợp hoặc self-managed Linux runner.
2. Nếu dùng self-managed runner cho job smoke, chuẩn bị DinD privileged/TLS cert volume;
   không expose Docker daemon ra mạng công khai. Kiểm tra khả năng runner trước khi chạy pipeline.
3. Tạo SSH deploy key riêng; public key cấp write trên GitLab. Private key chỉ lưu trong GitHub secret.
4. Thêm GITLAB_SSH_URL variable, GITLAB_DEPLOY_KEY và GITLAB_KNOWN_HOSTS secrets vào GitHub repo.
5. Commit/review/push source trên nhánh; xác nhận Actions sync thành công rồi GitLab pipeline cùng SHA.
6. Clone từ remote vào thư mục mới, chạy check.ps1 và smoke.ps1; lưu pipeline URL/SHA vào tasks/plan.md.

Tạo GitLab project trống, không README. Tạo SSH deploy key riêng, thêm public key vào GitLab với write access. Repo GitHub: variable GITLAB_SSH_URL (git@gitlab.com:namespace/project.git), secrets GITLAB_DEPLOY_KEY (private key), GITLAB_KNOWN_HOSTS (verified SSH host key line).
Xác minh fingerprint với tài liệu GitLab trước khi lưu known_hosts; không tắt host checking.
Chỉ đồng bộ một chiều, không edit GitLab. Actions push current branch/tag; không force, không mirror toàn refs, không tự xóa nhánh. Nếu rebase gây non-fast-forward, xử lý explicit sau khi đối chiếu lịch sử.
Deploy key phải được phép push protected main trên GitLab, hoặc giữ mirror main unprotected trong repo chỉ cấp quyền cho người sở hữu.
GitLab hosted Linux runner cho checks và Docker-in-Docker smoke. Self-managed runner phải bật privileged DinD với TLS cert volume theo GitLab docs.
Không hỗ trợ fork PR trong mốc này. Không cần Premium pull mirroring.
Trước merge: so sánh full SHA nhánh GitHub với CI_COMMIT_SHA pipeline GitLab thành công. Merge commit mới trên main cũng phải được CI kiểm tra.
Không có credential/project URL thì chỉ nghiệm thu cấu hình local, chưa tuyên bố remote CI pass.
Artifacts lưu 7 ngày; không mua compute thêm trong kế hoạch. Hosted quota hết: dừng remote jobs, dùng local checks hoặc cấu hình runner riêng.

## Troubleshooting
- Port 8000/5173 bận: set API_PORT/WEB_PORT trong .env.
- Readiness 503: xem docker compose logs migrate api postgres. DB phải có alembic head.
- Broker outage: API vẫn live/ready nếu DB tốt; worker/publisher log unavailable và tự probe lại.
- Scheduler probe chỉ cần DB; worker/publisher probe cần cả DB và broker.
- Schema không đúng: chạy docker compose run --rm migrate; không tự sửa bảng.
- Frontend chạy native: đặt FLOWFORGE_API_PROXY=http://localhost:8000 trước npm run dev. Proxy /api và /health dùng chung target; Compose mặc định http://api:8000.

## Migration và rollback
Chỉ thử downgrade base trên project test disposable, tuyệt đối không dùng DB có dữ liệu cần giữ.
Code rollback: checkout revision đã biết, rebuild; trước rollback schema phải kiểm tra compatibility và backup. Migration identity downgrade xóa toàn bộ ba bảng.
Backup local: docker compose exec -T postgres pg_dump -U flowforge -d flowforge -Fc > backup.dump bằng shell hỗ trợ binary redirection. PowerShell 7.4+ cần thiết cho native binary redirection; bản cũ dùng docker cp từ file trong container.
Restore vào DB mới, không ghi đè DB hiện hữu. Ví dụ tạo DB restore_check bằng createdb, docker cp dump vào container rồi pg_restore -U flowforge -d restore_check /tmp/backup.dump.
Sau kiểm chứng chỉ xóa tài nguyên project test được chỉ định; không docker system prune.

## Developer migration workflow

From backend/: `uv run alembic revision -m "describe change"`, edit upgrade/downgrade,
then test on disposable PostgreSQL. `uv run alembic upgrade head --sql` renders SQL without DB access.
script.py.mako is included. Migrations are explicit SQL today; autogenerate is not enabled because
there are no ORM models. When introducing models, import their shared Base.metadata into env.py
and verify autogenerated diffs; never configure an empty metadata object that proposes dropping tables.
0002_identity_guards rejects noncanonical emails or duplicate OWNER memberships. Inspect/report
dirty data first and resolve intentionally; do not silently normalize, merge or delete accounts in migrations.

## Scaffold verification and health

`./scripts/smoke.ps1` wraps `uv run --frozen --project backend python scripts/verify_stack.py`.
Each invocation generates ff-foundation-<random>, uses .env.example, free ports and isolated image tags/volumes.
It builds API then frontend sequentially, checks PostgreSQL constraints and frontend health proxy,
stops/restarts ONLY its broker/DB, verifies readiness/probes, SIGTERM and base/old/dirty-data/head upgrades.
Logs/results are under reports/<project>; finally removes only that project's containers and test volumes.
No persistent development DB is migrated or downgraded by this command.

--probe checks current dependencies. --health checks the role's successful-loop marker is <20s old.
The loop removes the marker after a failed probe or graceful stop. Compose background healthchecks
therefore detect unavailable/stalled loops. These remain scaffold loops, not execution readiness.
When execution is implemented, successful iterations must update this marker after actual role work.
Frontend has a proxy-aware HTTP healthcheck so --wait includes Vite readiness, not just container startup.

Stack test 2f7b5e9d4d6b đã cleanup và xác nhận sau restart ngày 2026-11-15. Lệnh đã dùng:
`docker compose --env-file .env.example -p ff-foundation-2f7b5e9d4d6b down --volumes --remove-orphans`.
This is a named disposable test project only; never substitute the development project's name.

## Gates and remote setup

Frontend lint is ESLint + React Hooks rules; typecheck is a separate TypeScript command.
Backend contract coverage >=80%, pip-audit of pinned exported dependencies and npm high-severity
audits are in local/CI checks. Add future engine modules to coverage; no skips/suppressions to pass.
Run check.ps1 and smoke.ps1 sequentially on memory-constrained machines.
Remote GitLab success and fresh remote clone remain pending until configuration/commit/push are completed.
Config files alone do not prove remote CI. tasks/plan.md tracks the current evidence and pending items.
